## タイムライン (2026-09-10)

## 原因の分析 (根本原因は未確定)

除外リストには `-anthropic.com, -*.anthropic.com, -claude.ai, -*.claude.ai` が
**含まれていた**にもかかわらず接続不能になった。有力仮説は次の順:

1. **hostname 行のサイズまたは解析挙動**: 生成行は 16,582 bytes・約 920 項目。
   ただし行全体が無視されれば、同じ行の広域 include も失われる。広域 include だけが
   残る説明には、部分採用・途中切り捨て等の挙動の証拠が必要であり、現時点では未取得。
   事故時の行では -anthropic.com は約 1.1KB、-claude.ai は約 3.1KB の位置にあるため、
   単純な 4KB 切り捨てでは両方の除外消失を説明できない。
2. **除外対象の不足**: アプリが未列挙のホストへ接続していた可能性。実際に失敗した
   ホストと TLS エラーを特定して検証する必要がある。
3. **設定合成・MITM の性能や実装挙動**: 複数モジュールの合成や大規模 hostname の
   処理で予期しない動作をした可能性。実効設定の記録が必要。

確認できた事実は「広域化した設定の適用後に接続不能となり、ロールバックで復旧した」
こと。Shadowrocket の解析限界、TLS で失敗した正確な理由、他アプリへの影響範囲は未確定。
検証する場合は本番端末の再広域化ではなく隔離環境で、項目位置と総バイト数を独立に変え、
接続先・エラー・設定の実効値を記録する。

いずれの仮説でも共通する教訓は「**この規模の hostname 行は実機で未検証のまま
本番投入してはならなかった**」こと。エミュレータは hostname 解析を自前実装して
いるため、SR 本体の解析限界を検出できない (検証ギャップ)。

## 寄与要因

- **実機カナリア手順の欠如**: 広域化のような影響全域の変更を、段階的適用
  (まず除外リスト縮小版で試す等) なしに一括投入した
- **エミュレータの検証範囲の過信**: サイト描画は検証できるが、SR 本体の
  conf/module 解析限界・アプリ (非ブラウザ) の TLS 挙動は検証できない
- **当日中の設計往復**: 同日に 許可リスト化→昇格運用→広域化 と3回の方針転換を行い、
  各段の実機検証が1サイクルずつしか行われなかった

## 実施した復旧・恒久対応

1. adkill_mitm.sgmodule を 3bc45ca の内容に復元 (MITM 許可リスト / [Script] は
   HTTPS 全ホスト文書 / newsdig は MITM 除外 + スタブ / SHA 固定 8ab78744 維持)
2. 唯一の追加差分として平文 HTTP 対策: [Script] pattern を
   「HTTPS 全ホスト + 平文 HTTP は neverssl.com のみ」に変更
   (blog.livedoor.jp 実機応答死の再発防止。基本設計は 3bc45ca から不変)
3. 広域 MITM 方式は「ロールバック済み・再使用禁止」として docs に明記。
   生成ツール (build_mitm_exclusions.py) は棚上げ資材として保持
4. rules_test に第10報の不変条件 (平文 HTTP 既定拒否 / HTTPS 広域維持 /
   Ad-Shield リライト整合) を追加。全 234 件パス
5. エミュレータで復元構成を6サイト検証 (example 注入 / livedoor HTTP 無傷 /
   trafficnews 注入 / newsdig 壁なし / hamusoku・mercari 無傷)

## 再発防止策

1. **hostname / pattern の規模ガード**: rules_test に「hostname 行は 4KB・項目数 200 を
   超えたら FAIL」の上限チェックを追加する。これは保守的な運用上限であり、SR の実測上限ではない。
   追補: conf/module の両方と合成後を検査し、審査済み MITM パターン以外の追加も拒否する。
2. **影響全域の変更は段階投入**: MITM 対象の大幅拡大を伴う変更は、(a) まず現行 +
   数ホストの小差分で実機確認 → (b) 拡大、の2段階を必須とする (docs に手順化)
3. **アプリ疎通の確認項目化**: モジュール/conf 変更後の確認リストに
   「Claude・LINE・決済アプリの疎通」を常設 (docs のチェックリストに追加済み)
4. **検証結果を次の拡大の条件にする**: 経過日数ではなく、実効設定・アプリ疎通・
   記事表示・復旧手順の実機確認が揃うまで次の拡大を行わない。確認項目は
   [安全性修正の適用条件](adversarial-hardening.md) を参照。

## 学び

許可リスト方式 (3bc45ca) は「未知サイトの快適性」を犠牲にする代わりに、
**復号による影響範囲を限定する**。DNS、外部ルール、UDP/443 遮断や
許可対象内の本文バッファリングには別の障害リスクが残る。今日の一連の往復は、その犠牲を取り戻そうとする
どの方向 (ホスト昇格・広域化) にも実機でのコストがあることを示した。
未知サイトのコスメティックが必要になった場合の正攻法は、SR の MITM ではなく
ブラウザ拡張層 (Safari + コンテンツブロッカー等) である。
